Bank AI Assistant Architecture

An enterprise knowledge assistant for Commercial Bank staff. It answers questions over policies, runbooks, incident reports and specs. A LangGraph supervisor coordinates specialist agents, a recursive research agent handles corpus-wide questions, and every tool call passes through a gateway the model cannot bypass.

orchestration / streaming security enforcement (code, not prompts) component / backend
01 · SYSTEM VIEW

Five layers, one trust boundary

The browser never talks to the agents directly. FastAPI authenticates, rate-limits and screens each request, then streams two kinds of events back over one SSE channel: answer tokens for the chat window and state events for the activity panel. The agents can reach backends only through the tool gateway, which takes the user's role and data-access filter from the authenticated request, never from model output.

02 · AGENT GRAPH

Supervisor loop with a guarded exit

The supervisor turns the question into a short plan and routes one step at a time. Workers write results into shared state through reducers and hand control back, so the supervisor can re-plan when a step fails or returns little. The loop is capped at four hops. The answer leaves the graph only after the output guard has checked every citation against evidence actually retrieved in this turn.

03 · RECURSIVE LANGUAGE MODEL

The research agent never reads the corpus

For questions like "summarize last year's payment outages and recurring root causes", putting documents into the prompt fails at scale. The research agent sees only a metadata catalog. It writes a small Python search plan, the sandbox runs it, and each batch of matching documents goes to its own sub-agent. A sub-agent whose batch is still too large splits it and recurses. The parent model only ever sees compact findings.

Example plan the model generates

# exposed names only: catalog, today, timedelta,
# grep, bm25_rank, chunk, emit — no imports, no I/O
hits = [d for d in catalog
        if d.document_type == "incident"
        and d.created_date >= today - timedelta(days=365)
        and {"payments", "cards"} & set(d.tags)]
ranked = bm25_rank(hits, "payment failure root cause")
emit(batches=chunk(ranked, size=8),
     task="extract root causes with evidence")

Why this counts as RLM, not just map-reduce

  • The model chooses the decomposition by writing code over the collection, rather than following a fixed pipeline.
  • Sub-calls are themselves agents that can split and recurse, with depth and token budgets in state.
  • Only the catalog the user is entitled to is loaded into the sandbox, so the plan cannot select restricted documents.
  • The plan, each batch and each finding appear as separate spans in LangSmith and as steps in the activity panel.
04 · RETRIEVAL

Hybrid search in one Pinecone index

Each chunk is stored with a dense embedding and a BM25 sparse vector in a dotproduct index. The query scales both sides by α before searching, so a single query returns the weighted combination of both scores.

score = α · dense(q, d) + (1 − α) · bm25(q, d) α = 0.6 by default, 0.3 for ID-like queries ("INC-2041")

Index layout

  • Namespaces by department: payments, platform, security, hr, product. Cross-department questions query namespaces in parallel with asyncio.gather and merge.
  • Metadata: doc_id, title, section, department, document_type, access_level, created_date, created_ts (epoch int for range filters), tags, severity, services.
  • Chunking: one chunk per ## section, so a citation points at a named section. Sections over 350 words split on paragraphs with one paragraph of overlap.

Query path

  • Supervisor extracts filters (type, date range, department) as a typed object.
  • Gateway adds access_level ∈ allowed(role); the model's filter can narrow this, never widen it.
  • Top 20 hybrid hits are reranked to the top 6 by Pinecone's hosted bge-reranker-v2-m3 cross-encoder.
  • Each passage carries a [doc_id §section] tag that the output guard checks against the answer's citations.
05 · ACCESS CONTROL

Roles decide which tools the model can see

Tools are filtered by role before they are bound to the model, so a Viewer's model never sees an admin tool in its schema. The gateway checks the role again at execution time in case a tool name is injected or hallucinated. Document access is a second axis, enforced as a Pinecone metadata filter.

07 · MEMORY

Short-term: the session

A LangGraph checkpointer keyed by thread_id stores full graph state after every node, so a follow-up like "what about the card ones?" resolves against the previous plan and evidence. After eight turns, older messages are folded into a running summary to keep the prompt bounded. The checkpoint is also what lets a HITL interrupt resume minutes later.

Long-term: the user

A LangGraph Store namespaced as ("users", user_id) keeps durable facts such as department, recurring topics and preferred answer format. Only memory_write writes to it, after the output guard passes, so a rejected or injected answer never becomes a memory. Recall lists only that user's namespace.

09 · DECISIONS & ASSUMPTIONS

Model selection

  • Large model (e.g. Claude Sonnet) for the supervisor and response agent: reliable tool calling and structured output matter most where routing and the final answer are decided.
  • Small model (e.g. Claude Haiku) for batch analyzers and guard classifiers: they run N times per question, so cost and latency multiply.
  • Embeddings: Pinecone Inference multilingual-e5-large (1,024-d), so one vector-store key covers embeddings, search and reranking. BM25 sparse vectors are computed locally and double as the offline index.
  • Fallback: a second provider behind the same interface, so an outage changes cost, not availability.

Assumptions and trade-offs

  • Hardcoded users with JWT (option A). Keycloak adds setup time without changing the authorization design.
  • Corpus is synthetic: about 60 documents across six types, with planted recurring root causes so the RLM output can be verified.
  • The RLM sandbox is internal to the research agent and available to all roles, because it only reads the user's already-filtered catalog. The user-facing python_analysis tool stays Analyst-only.
  • SQLite holds checkpoints and the memory store, in Docker Compose too. Moving to Postgres is a constructor change.
  • The sandbox (AST allow-list, fresh interpreter with an empty environment, CPU, memory and time limits) is adequate for a POC; production would add gVisor or a managed sandbox.
  • The custom graph is built on LangGraph directly rather than the deepagents package, to keep every node explicit and traceable.
